# Comps — Lumina-style implementation control pack

This pack adds the missing **implementation-control layer** around the existing Comps docs.

It does **not** replace the existing:
- `README.md`
- `docs/PRD.md`
- `docs/ARCHITECTURE.md`
- `docs/BIG_AUDIT.md`
- `docs/step2-plan.md`
- `docs/agent-notes.md`
- `AGENTS.md` generated by Next.js

Add the files in this pack to the repo at the same relative paths.

## Why these files exist

Comps already has a strong PRD, architecture, Step 2 plan, and build audit. What it lacks compared with Lumina is the layer that makes a coding agent behave predictably across the **whole project**:

1. `CLAUDE.md` — root operating contract for Claude Code.
2. `docs/SPEC.md` — exhaustive, durable source of truth for behavior and failure modes.
3. `docs/DESIGN.md` — explicit component boundaries, state ownership, communication, and trade-offs.
4. `docs/step3-plan.md` — detailed payments + usage implementation plan.
5. `docs/step4-plan.md` — detailed frontend + QA implementation plan.
6. `docs/step5-plan.md` — freeze, write-up, demo, and presentation plan.
7. `eval/expectations.json` — declared budgets and invariants.
8. `eval/cases.json` — named agent and integration cases.
9. `eval/README.md` — the gate order and how to prove the build.

## Authority order

When two sources disagree, use this order:

1. Executable code contracts and persisted schema:
   - `lib/agent/types.ts`
   - tool JSON schemas
   - `supabase/migrations/`
   - `lib/plans.ts`
2. `docs/SPEC.md`
3. `docs/ARCHITECTURE.md` and `docs/DESIGN.md`
4. The active step plan (`docs/stepN-plan.md`)
5. `docs/BIG_AUDIT.md` for actual current build status
6. `docs/PRD.md`
7. `README.md`

If a lower-ranked document is stale, update it after the implementation is verified. Do not silently make two sources disagree.

## Recommended workflow from here

1. Add this pack.
2. Review and commit the docs alone.
3. Close the remaining Step 2 verification items in `BIG_AUDIT.md`.
4. Give Claude Code: `CLAUDE.md`, `docs/SPEC.md`, `docs/ARCHITECTURE.md`, `docs/BIG_AUDIT.md`, and `docs/step3-plan.md`.
5. Build Step 3 one component at a time.
6. Run the gates in `eval/README.md`.
7. Update `BIG_AUDIT.md` after every verified component.
8. Only then move to Step 4.

The purpose is not to create paperwork. The purpose is to make every code change traceable to an explicit requirement and every "done" claim provable by a test.
